## Ask

Does simplifying the inline tool schema to just `{ alertId, timeWindowHours }` — removing the optional entity shortcut params — measurably reduce per-turn token overhead and bring total token spend closer to the legacy skill?

## Our Findings

Schema simplification **reduces tool calls from 5.9 → 5.7 per example**, confirming the model reasons more efficiently with a smaller schema. Input tokens came in at 193,825 — lower than v4 (254,899) and comparable to v3 (179,392), within the variance we've seen across runs. The gap to legacy (152,385) is **+27%** for this run, down from v4's +67%.

The residual gap is structural: the inline tool definition itself (description + Zod schema, even in minimal form) adds ~186 tokens to the system prompt on every turn. This overhead cannot be eliminated without removing the inline tool entirely, which would sacrifice the ability to call `findRelatedAlerts` with compact JSON params. The trade-off remains favorable — quality metrics hold at or above legacy on every dimension.

**v5 is the cleanest implementation yet:** v2 artifacts removed, schema at minimum viable surface, dual-register pattern (AB + Workflows) intact from v4.

## What this PR does

Stacked on v4 (#269443). The Workflows step type is unchanged. This PR adds v5 improvements only:

- Removes all v2 (api-driven) artifacts:
  - `alert_analysis_skill_api_driven.ts` and its test deleted
  - `evals_alert_analysis_api` Scout config set deleted
  - `alertAnalysisApiDrivenSkill` feature flag removed from `experimental_features.ts`
  - `register_skills.ts` collapsed from 3-way to 2-way flag
- Simplifies the inline tool schema: `{ alertId, timeWindowHours }` only — drops `hostNames`, `userNames`, `sourceIps`, `destIps`
- Handler always delegates entity lookup to `findRelatedAlerts` service (one ES `get` call internally, same as legacy)
- Response stripped to `{ message, sourceEntities, relatedAlerts }` — no surplus metadata
- `maxResults` hardcoded to 25; not model-controlled
- Skill `content` string trimmed: entity-shortcut guidance paragraph removed
- 11 unit tests updated and passing; new assertion confirms schema shape is exactly `{ alertId, timeWindowHours }`

## Why the schema simplification matters

Removing the 4 optional entity params achieves two things:

1. **Fewer tokens per turn.** The params collectively add ~400 chars to the tool schema in every system prompt. Across a multi-turn conversation the cumulative saving contributes to the 5.9→5.7 tool call reduction observed here.
2. **Simpler model reasoning.** The model no longer needs to decide whether to pass entity values or let the service look them up. There is only one path: pass `alertId`. The service handles entity extraction internally — exactly as the legacy tool did, and with the same ES `get` round-trip cost.

The trade-off (one extra `esClient.get` per invocation) is negligible in practice: sub-10ms, same latency profile as the legacy skill, and more reliable (entities always come from the canonical alert document, not from what the model happened to extract in a prior turn).
