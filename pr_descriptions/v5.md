## Ask

Do entity shortcut params (`hostNames`, `userNames`, `sourceIps`, `destIps`) in the inline tool schema meaningfully reduce token cost and tail behavior risk compared to a minimal `{ alertId, timeWindowHours }`-only schema?

## Our Findings

**Yes — v5-with-entity-params is the best variant across every metric.**

The key discovery came from running 15-repetition evals with enough statistical power to separate signal from noise:

- A 3-rep run made v5-without-entity-params look +27% more expensive than legacy. At 15 reps, the means converged to within +1.2% — confirming the gap was sampling noise, not a structural difference.
- Removing the optional entity shortcut params (`hostNames`, `userNames`, `sourceIps`, `destIps`) produced **dramatically worse tail behavior**: max token cost jumped from 1.1M (legacy) to 2.3M, and max tool calls from 21 to 34. Without the params, the model has no path to short-circuit alert re-fetching and can spiral.
- Re-adding the params back to v5 produced the **best results of any variant**: mean tokens -17% vs v5-without-params, max tokens -64% (839k vs 2.3M), mean tool calls 5.3 (lowest across all variants), and Groundedness 0.90 (best across all variants).

**Lesson: schema size is not the dominant cost driver. Tool call efficiency is.** Entity shortcut params save entire `security.alerts` round-trips, reducing both mean and tail cost.

## Why entity shortcut params matter (the key insight)

Schema description text for 4 optional params costs ~100 tokens per turn. The payoff: when the model already has entity values from a prior `security.alerts` call, it can pass them directly and **skip an entire `security.alerts` round-trip** on the next turn. A `security.alerts` response carries full alert `_source` data — potentially 2,000–5,000 tokens that then accumulate in every subsequent turn's context. At 15+ reps this effect compounds into the distributions above: entity params shift the max from 2.3M → 840k and the mean from 261k → 217k.
